# Java 数据安全检查

检查 Java 应用中敏感数据如何经过请求、授权、查询、修改和输出。本 skill 聚焦数据级授权：数据归属边界（水平越权/IDOR）与敏感数据输出；功能级授权（角色、权限注解，如 `@PreAuthorize`）不在本 skill 检查范围，发现明显缺失时可提示，但不作为系统性检查项。检查方式为静态代码审查：仅基于代码与配置证据下结论，不执行动态测试或运行时验证；无法静态确认的结论，在报告中标注待核实。以当前仓库实际使用的 Web 框架、数据访问方式和脱敏库为准理解代码：可以使用通用的 Java/Spring 注解与类型作为线索，但不要假设仓库存在特定 Maven 模块、配置项、业务基类或自定义校验接口。先读实现，再判断语义。

## 检查步骤

1. 阅读适用的安全要求，确认检查范围、账号角色、可信身份上下文，以及明确批准的公开场景。未说明的行为不能默认豁免。
2. 审查开始前先确定**资源归属维度**（见 2.1）：每类账号以什么字段划定数据边界、是否构成层级、哪些场景允许跨归属访问。归属不明确时向用户确认，不自行假设。
3. 从 Controller 路由和方法入手，追踪参数 DTO、Service、Mapper/Repository、SQL、关联查询、返回 DTO 与序列化过程；同时检查文件下载、模板渲染、消息和批处理等非 JSON 输出路径。
4. 覆盖所有读写入口：`@GetMapping`、`@PostMapping`、`@PutMapping`、`@PatchMapping`、`@DeleteMapping`，以及通过 `@RequestMapping` 声明的接口。按实际 HTTP method 判断行为，不能只看注解名称。
5. 核实每个入口的数据范围是否取自可信的服务端身份，并真正作用于查询或修改条件。跟进自定义校验方法、基类方法和拦截器的实现，不要凭方法名或注释下结论。
6. 验证敏感字段在实际输出路径上完成脱敏或最小化，并覆盖失败、空值、分页、嵌套对象、导出和异常分支。
7. 用代码证据支撑结论，不执行动态测试或运行时验证。报告中给出文件位置、调用链、可利用场景、影响、修复建议与覆盖缺口；不要记录真实敏感值。

## 一、敏感数据脱敏

### 1.1 脱敏字段范围

按字段真实含义判定，不按字段名判定。脱敏只发生在前后端交互。

**必须脱敏**

| 类别 | 字段 |
|------|------|
| 身份证件 | 居民身份证号、驾驶证号、护照号、港澳台通行证号、外国人永久居留证号 |
| 联系方式 | 手机号、固定电话、传真、电子邮箱 |
| 地址位置 | 住址、户籍地址、联系地址、精确到门牌的经营场所地址、经纬度与 GPS 坐标 |
| 金融信息 | 银行账号、银行卡号、支付账号 |

**无需脱敏**

| 类别 | 字段 |
|------|------|
| 主体名称 | 企业名称、机构名称、分支机构名称 |
| 主体与车辆标识 | 统一社会信用代码、组织机构代码、经营许可证号、业务证照编号、车牌号 |
| 人员姓名 | 法定代表人、负责人、经办人、联系人等各类姓名 |
| 业务编号 | 申请编号、案号、档案号、流水号 |
| 日志 | 日志输出暂时不考虑脱敏，脱敏只发生在前后端交互 |


### 1.2 追踪与验证

沿 DTO 和对象映射追踪敏感字段：请求 DTO、Service 内部模型、实体、响应 DTO、嵌套对象和导出模型。对返回前端的字段，确认项目所用脱敏注解与策略覆盖了实际序列化路径，例如：

```java
@Sensitive(strategy = SensitiveStrategy.ID_CARD)
private String idCertNum;

@Sensitive(strategy = SensitiveStrategy.MOBILE_PHONE)
private String mobile;

@Sensitive(strategy = SensitiveStrategy.ADDRESS)
private String address;
```

策略枚举、注解属性和生效条件以仓库依赖的脱敏库定义为准。需要时检查 `condition`、密文伴随字段等选项的真实语义，不能假设"加了注解就一定生效"；沿序列化器配置与调用链静态确认注解会被处理，代码证据不足时在报告中标注待核实。

### 1.3 逐项检查

- **策略匹配语义**：是否按字段真实含义选择策略。手机号、固话、地址、证件号各用对应策略；业务编号、企业名称、人员姓名等无需脱敏字段不得套用脱敏策略。
- **模型覆盖**：列表、详情、搜索、分页、统计、导出等不同响应模型是否都覆盖敏感字段，尤其关注手工组装或逐字段复制的 DTO。
- **绕过路径**：是否存在跳过脱敏的注解、序列化器、手工拼装 JSON、模板渲染或直接返回实体的情况，并确认其业务必要性与披露范围；错误响应、异常信息同样不得暴露敏感原值。
- **条件与开关**：脱敏条件或开关在目标运行环境是否生效。结论依赖配置时，应核对实际配置来源与有效值，不要把某项目的配置键或默认值当作通用约定。
- **非 JSON 输出**：文档、Excel、CSV、PDF 和消息等，是否在内容离开可信边界前完成处理。
- **原值保护**：不要为内部业务处理过早破坏原值，也不要让原值流入无权访问的输出。

脱敏只能减少展示信息，不能替代访问控制、加密或数据最小化；反之，内部流程需要原始字段，也不意味着可以把原值原样返回给调用方。

## 二、数据访问边界

越权检查沿一条主线推进：**数据属于谁（2.1）→ 可访问范围怎么算（2.2）→ 范围条件在入口怎么落实（2.3）→ 条件是否落到实际 SQL（2.4）**。写接口与批量操作另有附加检查（2.5、2.6），被复用的校验代码单独核对失败关闭语义（2.7）。

### 2.1 审查前置：确认资源归属维度

越权判定依赖"数据属于谁"，归属维度不同，判定标准完全不同。审查开始前先与用户确认，确认结果作为后续所有接口的判定基准；未确认的维度按"未知"标注，不得默认放行。

常见归属维度：

| 归属维度 | 典型字段 | 说明 |
|---------|---------|------|
| 管辖机构 | `orgId`、`orgCode` | 层级机构，授权范围按业务规则（仅本级 / 本级 + 下级） |
| 管理部门 | `deptId`、`manageDeptId` | 业务条线部门，授权规则独立于机构树，不套用层级继承 |
| 企业/业户 | `ownerId`、`socialCreditCode` | 企业账号的数据边界 |
| 从业人员/驾驶员 | `pracId`、`idCertNum` | 个人账号只能访问本人数据 |
| 区域 | `areaCode` | 行政区划，可与机构维度并存 |
| 车辆/设备 | `vehicleNum`、`plateColor` | 按归属企业或归属人校验 |


### 2.2 可访问范围：层级规则与实现

在归属清单的基础上，逐维度明确每类账号可访问的记录、字段与操作。先按层级规则确定范围语义，再确认仓库用什么实现表达层级。

**层级规则**

组织边界可能按层级继承，但必须按明确的业务规则计算，**不能把"同属一棵组织树"视为都可访问**。认证成功不代表可以访问请求中任意给定的资源 ID、归属字段或其他业务标识。以三级机构加一个平级机构为例：

```text
机构1（上级）        orgCode = JTT_
  └─ 机构2（当前登录）  orgCode = JTT_NJ_
       └─ 机构3（下级）  orgCode = JTT_NJ_JN_
机构4（与机构2平级）  orgCode = JTT_SZ_
```

- 机构2 只能访问机构2 与机构3。
- 不能访问机构1（上级），也不能访问机构4（平级）。
- 若机构3还有下级，按规则一并纳入。
- 平级、上级数据不因"共享祖先"、"可见机构树"或客户端传入的机构编号而放行。

若具体系统定义了不同的层级授权规则，以其明确的业务策略为准，并据此验证实现。

**实现方式：前缀式层级编码**

以下模式仅当仓库实际采用时适用，作为识别线索而非通用假设；机构表结构与层级表达方式以仓库实际代码为准。一种典型实现是机构表：

```java
/**
 * 系统管理-管辖机构
 *
 * @author taogang
 * @date 2026-07-15 08:45:29
 */
@Data
@TableName("SYS_ORGANIZE")
public class SysOrganize {

    /** 机构Id */
    @TableId(type = IdType.ASSIGN_ID)
    private String orgId;

    /** 机构名称 */
    private String orgName;

    /** 机构代码 */
    private String orgCode;

    // 其他属性
}
```

其中 `orgCode` 采用前缀式层级编码，例如：江苏交通厅 `JTT_`、南京市交通局 `JTT_NJ_`、江宁区交通局 `JTT_NJ_JN_`。编码本身即可反映上下级关系，因此可用前缀匹配计算可访问范围，但需同时确认分隔符与末位格式：若以不带尾部分隔符的 `JTT_NJ` 做前缀匹配，会误匹配到 `JTT_NJX_` 一类同前缀机构；按含尾部分隔符的 `JTT_NJ_` 匹配则不会。以仓库实际的编码规范核对。

### 2.3 入口侧：可信身份与范围条件（强制）

Controller 是范围条件的第一落点。先确认身份来源可信，再核实范围条件如何注入并生效。

**身份获取与可信来源**

项目可能通过类似方式取得当前账号：

```java
// 当前登录人管辖机构 id
String orgId = AccessContextHolder.getUserInfo().getOrgId();
// 当前登录人管辖机构编码
String orgCode = AccessContextHolder.getUserInfo().getOrgCode();
```

- 上下文由认证链可靠建立，不能由客户端直接伪造。
- `account` 及必需的范围字段非空、有效。
- 若身份经网关请求头传入，网关会剥离客户端的同名请求头并写入已验证的值。

**orgCode 维度：currentOrgCode 强制注入（仓库约定）**

凡是涉及 SYS_ORGANIZE 机构维度的查询（查询机构表本身，或以 `orgCode` 过滤业务数据），Controller 必须注入默认查询条件 `currentOrgCode`，其唯一合法赋值来源是当前登录人机构编码：

```java
String orgCode = AccessContextHolder.getUserInfo().getOrgCode();
query.setCurrentOrgCode(orgCode);
```

- `currentOrgCode` 在 Controller 由 `AccessContextHolder.getUserInfo().getOrgCode()` 赋值；取自请求参数、前端 DTO 字段、硬编码或其他来源的，一律判为缺陷。
- 赋值后必须追踪到对应的 Mapper XML 或查询方法，确认条件真正进入 SQL（如按 2.2 前缀编码匹配本级与下级）；只在 Controller 设置字段、查询中不使用的，视为未生效。
- 若接口还接受前端传入的机构筛选，该值必须校验落在 `currentOrgCode` 派生的可访问范围内，不能替代其范围锚点作用（见 2.4）。

该约定是判定表中"无条件覆盖前端传值，直接以登录归属为准"模式在 `orgCode` 维度上的落地形态。

**其他归属维度：未传兜底或拒绝 + 传入校验**

按归属字段过滤的 GET 接口必须落实"未传则兜底或显式拒绝、传入则校验"两个分支（兜底还是拒绝，按 2.1 确认的业务约定），列表、分页、导出、统计接口无一例外：

```java
@GetMapping("/list")
public R<List<Xxx>> getResultList(XxxQuery query) {
    if (EmptyUtil.isEmpty(query.getOrgId())) {
        // 未传机构条件：用当前登录人的机构兜底，避免条件缺失退化为全量查询
        query.setOrgId(AccessContextHolder.getUserInfo().getOrgId());
    } else if (!canAccessOrg(query.getOrgId())) {
        // 传了机构条件：必须落在当前登录人可访问的范围内（含允许的下级）
        throw new NoStackBizException("查询的数据信息不是当前登录用户下的，禁止操作！");
    }
    return R.OK(xxxService.getResultList(query));
}
```

以 `orgCode` 为条件时，同一模式对应 `getOrgCode()/setOrgCode`，由 `canAccessOrg` 按编码前缀或机构树判断可访问范围。

判定标准：

| 实现写法 | 结论 |
|---------|------|
| 无条件覆盖前端传值，直接以登录归属为准 | 通过（优先推荐） |
| 未传则兜底 + 传入则校验且覆盖允许范围 | 通过 |
| 未传则显式拒绝（与 2.1 确认的业务约定一致） | 通过（同样满足失败关闭） |
| 无兜底、无校验 | 缺陷：未传时全量，传入时可越界 |
| 只兜底、不校验 | 缺陷：可直接传他人归属值查询 |
| 只校验、未传时既不兜底也不拒绝 | 缺陷：未传时动态条件被跳过，退化为全量 |
| 有校验但只比对本级、未覆盖允许的下级或条线范围 | 缺陷：范围判断不完整 |

判断可写在 Controller，也可收在基类、切面或统一封装中，但必须对每个列表类接口生效；不能只在部分接口、部分分支执行。

### 2.4 读接口检查

列表、搜索、详情、关联查询、统计、计数和导出都要检查，按入口形态分组：

**列表、分页、统计、导出**

- **必检项**：未传兜底（或按 2.1 确认的约定显式拒绝）+ 传入校验（模式见 2.3），缺失即判为越权缺陷。
- **筛选与范围双约束**：以 `orgId` 限定的查询，先从可信上下文计算可访问范围。前端传入 `orgId` 时，既要有归属校验，也要把该值作为筛选条件；最终查询必须同时受"筛选条件"和"可信可访问范围"约束，不能校验完就直接按客户端值查。接口合同应写明筛选的是"该机构本身"还是"该机构及其下级"。
- **空值与失败关闭**：前端未传 `orgId` 时，必须把可信上下文派生的默认范围加入实际查询，或按 2.1 确认的约定显式拒绝请求，不能因空值跳过过滤；省略参数即全量返回的列表接口，一律视为缺陷。关键身份或归属字段缺失时应拒绝，不能因空值导致动态查询条件被忽略、扩大为全量。

**按归属或资源标识查询：目标校验（必检）**

凡请求中出现客户端可控、且决定"查谁的数据"的标识（路径变量、查询参数或请求体均可携带），就必须校验该目标落在当前账号可访问范围内，按 2.1 确认的归属清单逐维度适用：

- **按归属标识查询**：接口支持传 `ownerId`、`deptId`、`pracId`、`vehicleNum`、`socialCreditCode` 等归属字段时，不能拿来就直接查。例如传 `ownerId` 查询，先校验这个 `ownerId` 对应的业户是不是当前账号可查看的业户；查车辆信息时，先校验该车辆是否在当前账号可查看范围内。
- **按资源 ID 取数**：详情、修改前回显等按记录 ID 取数的场景，加载后校验该记录属于当前账号，或把资源 ID 与可信数据范围一并放入查询条件。

两种实现等价有效：

- **先校验再查询**：先按标识查出目标的归属字段，比对是否落在 2.2 计算的可访问范围内，不在则拒绝。
- **查询内约束**：把目标标识与可信范围条件一并写入 SQL，无权时返回空结果——"确保无权数据不可见"同样是合规处理。

无论哪种实现，最终查询仍须同时受目标标识与可信范围约束（同"筛选与范围双约束"），不能校验完就直接按客户端值查。

**追踪到实际查询**

- **字段真的进入 SQL**：追踪 Query/DTO 字段是否落到 Mapper/Repository。检查 MyBatis XML/注解 SQL、动态 `<if>`、Join、子查询、分页 count 与导出 SQL；JPA、QueryDSL 或其他访问层按其最终查询条件验证。
- **层级范围的真实生成**：组织层级过滤只含当前机构及规则允许的下级，明确排除平级与上级；核对机构树查询、递归条件或闭包表关系实际生成的范围，不能只检查客户端传入的机构编号。

**边界细节**

- **字段差异**：管理部门等字段应按其实际归属和授权关系单独计算，不能直接套用机构树规则。
- **关联对象**：关联记录、子对象和映射后字段遵循相同边界，父记录被授权不代表其全部关联记录可访问。
- **账号类型**：人员、车辆、企业、组织等关系要按账号类型分别检查，不能认为某一角色的校验天然覆盖其他角色。
- **超出范围**：应拒绝请求，或确保无权数据不可见，并遵循接口既有的错误语义。

### 2.5 写接口检查

覆盖创建、更新、删除、提交、指派、导入及批量操作：

- **受保护字段**：创建或导入时，所有者、归属企业、机构等字段应由服务端确定，或逐条校验请求数据。
- **更新与删除**：应作用于已校验的同一资源；优先把资源 ID 与可信归属条件一起放进实际 `UPDATE`/`DELETE` 条件，并处理影响行数为 0 的情况。
- **ID 一致性**：核对路由 ID、请求体 ID 和 Service 最终使用的 ID 是否一致；路径参数未参与任何校验时视为可疑，即使当前由请求体兜底。
- **状态变更**：作废、审核、提交、指派等"改状态"接口同样需要归属校验，不能因为不返回数据就当作低风险。
- **批量授权**：见 2.6。

### 2.6 批量操作

- 对每条记录执行授权，或确保批量查询/更新本身被可信范围约束。
- 只校验第一条、只检查集合中的一个对象、或由一个共享字段推断全部记录归属，均不足以证明安全。
- 混合归属的批次应明确"整体拒绝"或"逐条处理"，并避免通过返回结果泄露无权记录。

### 2.7 通用校验代码的失败关闭语义

检查所有被复用的校验方法：

- 空参数是否导致跳过检查。
- 校验查询是否真正关联了当前请求的资源 ID。
- 集合校验是否覆盖全部元素。
- 异常是否被吞掉。
- 包装方法是否只在部分分支执行授权。
- 被多个 Controller 或入口复用的 Service 方法：确认每个调用方都落实了归属范围条件，不能默认调用链上游已做校验。

对每个被调用的自定义方法查看实现，记录它**实际**保障的条件，而不是它名字暗示的条件。

## 三、公开接口与豁免

免登录、公开查询或跨组织查询应有明确业务目的和有限输出：

- 核实允许返回的具体字段、记录范围及责任方。
- 若项目存在白名单或审批记录，核对其内容与实际实现是否一致。
- 按风险检查枚举可能性、频率限制、统一错误信息和滥用监控。
- 公开场景不自动允许返回关联私有字段，也不自动允许执行写操作。

白名单记录、TODO、注释和接口命名都不能代替代码验证。若业务批准、数据范围或预期披露内容无法确认，列为待确认事项，并说明当前代码实际能暴露什么。

## 四、结果报告

报告开头先列出本次审查采用的**归属维度清单**及其来源（用户确认 / 代码推断），未确认的维度标注为待核实，再按敏感程度、受影响范围、调用者权限、可利用性以及读写影响评估严重程度。每个发现包含：

- **问题与严重程度**：简洁，与已证实的影响相称。
- **位置与证据**：Java 文件/行号，以及 Controller → Service → Mapper/SQL 或输出对象的相关调用链。
- **利用场景与影响**：调用方控制什么、可以绕过什么、能读取/推断/修改什么。
- **修复方向**：指出应在哪一层落实范围条件、对象校验或脱敏。
- **状态与置信度**：已确认、较可能，或需核实配置/业务策略/运行时行为。

避免记录真实身份证号、手机号、凭据、令牌和生产标识符。

没有发现问题时，说明实际检查过的接口与数据路径、核查过的代码证据、未覆盖范围及剩余不确定性；部分检查不得表述为完整审计。
